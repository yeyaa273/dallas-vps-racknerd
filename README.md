## 达拉斯的位置到底好在哪？先看延迟表

达拉斯服务器的价值在于延迟的“分布形状”——用户分散在全美时，它的最差情况最小；用户集中在某一侧海岸时，它输给本地机器。

光在光纤里每秒走约 20 万公里，每传 100 公里往返延迟大约多 1ms，而且城市之间的光纤从来不是直线铺设。这是物理下限，砸钱绕不过去。互联良好的有线线路，业界通常公布的往返延迟（RTT）大致如下：

| --- | --- |
| 达拉斯本地 | 2ms |
| 休斯敦 | 8ms |
| 芝加哥 | 23ms |
| 迈阿密 | 33ms |
| 洛杉矶 | 35ms |
| 纽约 | 36ms |
| 墨西哥城 | 48ms |
| 西雅图 | 50ms |
| 伦敦 | 112ms |
| 新加坡 | 215ms |

这些是商家通常公布的数值，拿它当地铁图用，别当成你家测速的结果。Wi-Fi 会加几毫秒，蜂窝网络加几十毫秒，互联差的住宅宽带甚至能让本来 15ms 的路径多出 30ms。

再看分布形状。北弗吉尼亚到纽约约 10ms、到洛杉矶约 62ms，两端差超过 50ms；洛杉矶正好相反，到纽约 68ms、本地 3ms。达拉斯落在 36ms 和 35ms，两头都不出彩，但也没有短板。用户集中在一个地方，就选当地机器；用户散布全国、或者你根本预测不了他们在哪，这种“没有短板”反而最值钱。顺带一提，墨西哥城 48ms 比美国东西海岸都近——拉美流量本来就有大量经过得州或佛罗里达中转，用达拉斯机器服务墨西哥、哥伦比亚（78ms）用户是合理操作。

达拉斯的运营商密度也会体现在实际链路里。著名的 Infomart 运营商机房就在 1950 North Stemmons Freeway，Equinix 2018 年以 8 亿美元买下它，DE-CIX 从 2016 年 11 月起在那里运营交换点。你的主机和用户的 ISP 接入同一个交换点，数据包只跨一个网络边界；接不进同一栋楼，就得交给 transit 提供商，可能先去阿什本或亚特兰大绕一圈再回来，每多一个网络就多一个晚上九点拥堵丢包的环节。

毫秒到底值多少钱？建一次 HTTPS 连接至少三次往返：TCP 握手一次、TLS 1.3 一次、发请求一次。35ms 延迟下，首字节回来之前已经过了 100ms。一个页面串行发 20 个 API 请求，就是 700ms 的累积。35ms 的 SSH 和 8ms 的 SSH 是两种体验；游戏服务器在 35ms 下通常没问题，到 140ms（比如圣保罗）就基本没法玩了。

## 大陆用户实际体验如何？别指望低延迟

大陆用户直连达拉斯，延迟不会低，面向大陆优化的线路也基本不落在达拉斯，这一点买之前要想清楚。

物理路径解释了大半问题：大陆流量先跨太平洋到美西登陆，再横穿美国到中南部。达拉斯公布到新加坡 215ms，反方向同理。更关键的是线路——目前面向大陆优化的回程线路（CN2 GIA、AS9929、CMIN2 这类）主要落在洛杉矶、圣何塞、香港和东京，很少有商家把这些线路铺到达拉斯。RackNerd 的达拉斯机器走常规国际线路，拿来做海外站、后台服务、自己用的工具没问题，指望“国内访问如本地般顺滑”是不现实的。

核心需求就是国内访问速度的话，方向应该换成美西、香港或日本的优化线路产品。市场上这类机型的常见配置是香港 CN2/CMI 直连（比如 DMIT 香港的 Premium 系列走 CN2/CTG 回程、Eyeball 系列走 CMI），或者东京的 CN2+9929+CMIN2 组合（比如 V.PS 东京 Performance Gen 2），价格比达拉斯特价高出一大截，但那是延迟的合理对价。

## 达拉斯为什么便宜：电价便宜，以及一张独立的电网

电力是数据中心最大的运营成本，得州的工业电价低于美国平均水平，这部分差价最后会体现在你的账单里。

便宜电的另一面是一张独立的电网。ERCOT（得州电力可靠性委员会）覆盖全州约 90% 的用电负荷，与北美其他电网不同步，只靠几条直流联络线和邻区相连，总容量约 1.2 GW——而 2026 年 7 月 22 日记录的峰值需求超过 91 GW。本地缺电时没法靠外部输入救急，2021 年 2 月冬季风暴 Uri 期间连续多天的轮流停电就是这么来的。

对服务器来说，关键的其实不是电网而是那栋楼。市政断电后，数据中心先靠 UPS 电池撑几分钟，然后切柴油发电机。下单前可以直接问商家四个问题，并要求书面答复：

1. 供电路径是 N+1 还是 2N？
2. 现场燃料储备满负载能跑多少小时？
3. 有没有签订优先燃料配送合同？
4. 上一次在实际负载下测试发电机是什么时候？

最后一个问题答不上来的商家，就是没测过。

天灾也值得说两句。2019 年 10 月 20 日，一场最大风速接近 140 mph 的 EF3 级龙卷风横穿达拉斯北部，留下 15 英里长的路径、约 15 亿美元损失，路径距离 Stemmons Freeway 数据中心走廊只有几英里。机房本体是无窗混凝土结构，扛得住；暴露在外面的是楼顶的冷凝器和冷却塔，大冰雹砸的正是它们。高温则是另一笔账：达拉斯 7、8 月长时间在 100°F（约 38°C）以上，制冷按当地设计日配置、温度能守住，但 8 月的 PUE 会上浮，成本已经含在价格里。真正要防的是热浪期间制冷故障——室外 40°C 时，失去制冷的机房几分钟内就会到关机温度。问供电冗余的时候，把制冷系统是不是 N+1 也一起问了。

这些风险的合理应对，是在另一个地点保留一份数据副本。同一栋楼里的备份，算不上异地备份。

## 下单前可以自己做的三件事

买之前可以先核实网络这一层：要 ASN、查 PeeringDB、跑一次 mtr，全程不花钱。

1. 向商家客服要 ASN（自治系统号），所有跑 BGP 的网络都有。
2. 拿 ASN 去 PeeringDB 查：它加入了哪些互联网交换点、入驻了哪些建筑。这些条目由网络自己维护，信息相对诚实。
3. 确认套餐所在的数据中心楼里有没有交换点——和交换点同楼但没接入，等于没沾光。
4. 从你和用户所在的网络 traceroute 到服务器 IP，数一数中途跨了几个网络。

机器到手后跑一条 `mtr -rwzc 100 你的服务器IP`。报告会为每一跳打印网络编号、丢包百分比和耗时。先看最后一行，那一行对应你的服务器；中间某跳丢包、末尾没丢，通常正常——路由器会降低对自身 ICMP 响应的优先级，那一跳的丢包率经常被高估。丢包从某一跳开始、一直持续到末尾，才是真故障，把报告附上开工单。
